One story: start with a single app and a single database, and add each piece only when a problem forces it. Running example: the movie ticketing app.

1

Monolith, and why split it

One app, one database. As it grows: one bug takes everything down, you cannot scale just one part, and big teams step on each other.

teach on the board
2

Microservices basics

Split by business area: Movie, Booking, Payment. Each service owns its own database and talks to others over APIs. Trade-off: independent deploys and scaling, but network calls, harder debugging and no JOINs across services.
